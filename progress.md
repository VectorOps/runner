# Runner v2 progress

Current implementation status and suggested next development horizon.

## Implemented

- [MCP integration](docs/config/mcp.md) supports configured POSIX stdio and Streamable HTTP servers, bounded catalog discovery, schema-backed tool bindings, text/images/structured results, and provisioned credential references. Daemon management and workflows share matching sessions with execution leases; standalone runners retain root-owned cleanup. Discovery and calls use recorded activities and existing tool approval; completed SQLite replay performs no MCP or credential I/O. Coverage includes stateful HTTP, server requests during SSE, deadlines, cancellation, startup rollback, process cleanup, malformed schemas, and catalog limits. No Knowlt integration is introduced.
- MCP configuration supports ordinary environment/header values, separate credential references, and discriminated none/header/authorization-code/client-credentials authentication. Client-credentials tokens use encrypted configuration-bound caches and serialized acquisition. Typed Python management and authenticated `mcp.*` RPCs expose listing, status, connection/login, discovery/refresh, content catalogs, disconnect/logout, and session-root overrides. Defaults and merge/replace root policies normalize paths to URIs; leased sessions reject destructive changes. Tool-list change notifications mark catalogs stale and notify hosts without mutating recorded workflow bindings. Opt-in weighted discovery covers original names, titles, descriptions, schemas, and source filters; recorded workflow convenience helpers cover tools, prompts, and resources.
- MCP prompt/resource catalogs and retrieval are recorded separately. Explicit selections and source checks constrain optional model tools; direct retrieval remains trusted workflow orchestration. Prompt roles, resource URI/MIME metadata, native images, and binary fallbacks survive replay. Descriptors are rechecked before live retrieval, and links are never automatically fetched. Coverage includes approval rejection, descriptor changes, pagination, content bounds, HTTP cancellation, and offline replay.
- MCP OAuth supports pre-registered public clients with authorization-code PKCE, pinned resource/issuer metadata, same-origin authorization/token endpoints, encrypted resource-bound profiles, and shared refresh. The existing host callback/RPC flow coordinates login without receiving tokens. Interactive waits retain execution attribution and sit outside MCP request/startup deadlines; a Bearer 401 permits one non-interactive refresh/retry. Coverage includes rejected metadata/redirects, host callbacks, suspension/restart, rotated-token publication under cancellation, secret isolation, and pre-OAuth replay identity compatibility.
- Dynamic MCP catalogs expose search-only visibility through `mcp.dynamic(...)` and `LLM.run(tool_set=...)`. Successful recorded search outcomes advance immutable, bounded activation only at complete-round boundaries; concrete tools retain independent approval. Catalog refresh is explicit. Coverage includes same-round hidden calls, strict failures, ordered activation, static/dynamic collisions, concurrent LLM isolation, changed-catalog replay mismatches, mandatory denials, and interrupted recovery.
- Built-in tools are forwarded through `vectorops.runner.api.tools`: `exec_tool`, `poll_process_tool`, `write_stdin_tool`, `kill_process_tool`, `list_processes_tool`, `read_file_tool`, `run_agent`, `update_plan_tool`, and `web_fetch_tool`. Process and file tools use the attached target environment; code discovery uses `rg` through `exec`, with no Knowlt integration. `run_agent` exposes permitted child workflows while `subworkflow_tool` remains compatible with existing callers and histories.
- File reads support bounded byte/line ranges, native complete PNG/JPEG/GIF/WebP image blocks, and lossless base64 for other binary content. Partial images are returned as base64 rather than invalid image blocks; PDF/document extraction is not implemented. Plans merge stable task ids, allow at most one active task, and reconstruct workflow-local state through recorded updates. Create one `update_plan_tool()` binding inside each workflow and reuse it across rounds.
- `web_fetch_tool` performs bounded async HTTP requests from the runner host, normalizes HTML to plain text, and returns native images or base64 for binary responses. It returns redirects without following them, reports HTTP errors and truncation, and caps response/request bodies at 1 MiB. It uses the host network, including private addresses, rather than a network sandbox; approval applies and arguments are persisted, so callers must not supply secrets in tool arguments.
- LLM generation and compaction attach payload-free, versioned metrics to existing activity snapshots and terminal steps. Connect catalog limits/prices support context and output budgets, remaining output headroom, and explicitly labeled USD cost estimates; provider usage retains its own completeness. Retry attempts survive failures, reset on unfinished recovery, and remain unchanged on terminal replay. Compaction records signed estimated context savings without changing its policy. Metrics are available through step events, history queries, and JSONL inspection without duplicating transcripts or adding credentials. Coverage includes missing/ambiguous models and rates, multimodal unknowns, overflow, retry/cancellation/replay, legacy records, SQLite round trips, and expanding summaries. See [LLM observability](docs/config/components.md#llm-observability).
- Tool approval responses accept optional `scope: "call" | "workflow"`, defaulting to a single call. Workflow approval atomically grants the exact tool name for the requesting workflow instance, without inheriting into children, siblings, or other executions. Grants survive restart/resume alongside mailbox answers, preserve mandatory checks and explicit pending confirmations, and add no policy activities. Coverage includes competing answers, malformed scopes, workflow filtering, isolation, outcome replay, and hard-crash recovery before tool-result commit. See [Workflow-scoped tool approval](docs/reference/control-protocol.md#workflow-scoped-tool-approval).
- The Python 3.13 uv project preserves the old project's dependency requirements and package layout.
- Pydantic models provide JSON-serializable workflow configuration and normalized step records.
- Predecessor references represent branching histories without copying existing steps.
- Typed operations represent child spawning, ordered joins, and workflow completion.
- Workspace setup supports `workflows/`, `data/`, and optional directory overrides in `config.toml`.
- The executor loads named async callables from workspace Python files with path validation.
- Executor sessions drive workflow operation requests through registered typed handlers.
- A persistent FIFO dispatcher owns request acceptance and replay ordering while a single supervisor handles fatal errors and cleanup.
- Local activity decorators bind arguments, apply defaults, and validate JSON-compatible inputs and results.
- Ordinary and streaming activities receive an explicit first-argument context with execution, workflow, and step identities.
- Activity identities are persisted before invocation and reused during interrupted recovery for implementation-owned idempotency.
- Streaming activities yield replacement snapshots and one final result while history retains only the latest step version.
- Completed streams replay without reinvocation, and interrupted streams restart under the same step identity.
- `@activity_wrapper` injects an `ActivityCall` helper into async functions and instance methods. Wrapper code always executes, while `run()` and `stream()` establish a single recorded activity boundary with explicit JSON inputs.
- Workflow-local `LLM` objects own opaque conversation state, expose detached history snapshots, and reconstruct deterministic state changes from recorded results during replay. New instances reset history, and overlapping mutations on one instance are rejected.
- LLM activity inputs contain instance identities and request digests rather than accumulated transcripts, preventing quadratic conversation duplication in saga storage and detecting changed requests during replay.
- The `connect` provider adapter accumulates streaming events into replacement snapshots, preserves final response metadata, resolves authentication at runtime, and rejects unsuccessful or missing terminal responses.
- Explicit named tool bindings derive schemas from Pydantic argument models. The workflow-side `invoke_tool` helper validates calls, optionally waits for per-call mailbox approval, and records execution independently of the LLM. Bounded LLM loops execute tools in parallel and append results in model-call order; tool exceptions become model-visible responses with unchanged error text by default. Strict exception handling is opt-in, while cancellation and runner infrastructure failures still propagate without appending a partial round.
- New workflows gate tools inside the recorded tool execution, with no policy activities or recorded policy decisions. A separate tool-name whitelist registry supports mandatory checks and auto-approval matchers; workspace `components.tools.approval` settings provide exact-name grants and explicit approve-all. Unlisted tools require durable host confirmation attached to the tool step. Completed results and rejections replay without reevaluating policy; pending requests and accepted answers survive recovery. Existing histories retain binding-local approval through a workflow format marker. See [Tool approval](docs/config/components.md#tool-approval).
- Opt-in measured compaction checks final provider input usage after successful responses, retains a configurable recent token tail at complete-exchange checkpoints, and updates the previous summary with newly excluded history. One forced compaction and generation retry can recover a context-length error without reexecuting tools or predicting request size. Provider usage remains immutable; derived checkpoints rebase from the selected prefix, not a target budget. Dedicated summary settings/output caps, validation before replacement, stable anchor identities, recorded model limits, and versioned activities preserve deterministic replay. Legacy character policies retain their original behavior. See [Measured compaction](docs/config/components.md#measured-compaction).
- History access is injected through an asynchronous protocol rather than an executor-owned step collection.
- Each execution retains its root and child workflow histories in `data/executions/<execution_id>/history.sqlite3`.
- Runner-owned `data/runner-state.json` stores the last execution identity and active execution IDs for restart discovery, with serialized updates and backward-compatible loading of last-pointer-only manifests.
- Each history database contains execution identity, lifecycle status, root configuration, and selected root and child heads.
- Durable step writes advance selected heads transactionally, independently of global runner state.
- Periodic execution checkpoints flush buffered snapshots and persist recovery metadata inside the history database.
- Explicit resume uses recorded execution configuration and checkpoint heads; the control service reconciles workspace state against retained histories and automatically recovers all executions whose persisted status is `running`, including when the manifest is missing.
- Exclusive project writer ownership prevents concurrent processes from conflicting over global state.
- Explicit cleanup removes terminal execution histories while preserving active executions and unrelated records.
- Optional age and count retention limits prune completed histories after successful execution while protecting the last execution.
- Transactional streaming updates rewrite one unfinished step while preserving its identity and immutable terminal outcome.
- SQLite replay uses indexed lookup and database-side path snapshots with bounded Python-side batches.
- Bounded LRU caches reduce repeated configuration and step lookups during execution.
- Write-behind buffering coalesces streaming snapshots and flushes periodically, on completion, or at runner shutdown.
- Replay streams selected history from the root and returns recorded outcomes without repeating activities.
- Continuation appends new descendants while preserving existing branches.
- Child workflows execute concurrently or sequentially with independent sessions and histories.
- Decorated async workflows compose with standard asyncio gather, tasks, waits, and task groups using function-derived persistent targets.
- Durable waiting joins preserve request order while children complete independently without regressing history heads.
- Executor step-event hooks expose accepted snapshots for future UI listeners without making progress part of workflow results.
- Joins reference exact child completion records and propagate or collect failures in invocation order.
- Explicit child replay heads support partial recovery and forks across multiple nesting levels.
- Cancellation closes replay streams, settles pending requests, and cancels owned child tasks.
- The transport-independent control service and client expose execution and mailbox operations over embedded or TCP connections.
- The built-in `vectorops.runner.api.mailbox.request_input` activity waits on a named channel with a JSON request payload and a text response by default, or a JSON response when requested.
- Mailboxes accept responses only for existing request IDs; channels classify requests without buffering unsolicited messages.
- Input requests and accepted responses persist in the execution database, and recovery reuses request identities and delivers accepted answers without asking again.
- Hosts can list pending requests with channel and workflow filters, inspect a request, and submit an atomic, idempotent response through `mailbox.list`, `mailbox.get`, and `mailbox.respond`.
- Live `mailbox.requested` and `mailbox.answered` notifications supplement durable queries; reconnecting hosts discover outstanding requests without relying on event replay.
- Host disconnects preserve waits. Service shutdown while input is pending preserves waits for restart, while explicit execution stops cancel them.
- Multiple input waits and independent root executions can run concurrently, including on the same channel. Input ownership and responses remain execution-specific, and rewinding an execution with pending requests is rejected.
- `vops-runner` starts workflows with JSON input and optional execution IDs, and resumes persisted executions after interruption.
- Read-only CLI status exposes persisted execution metadata and counts by operation and outcome across root, child, and retained branch histories while a writer is active.
- Full-execution JSONL export writes a versioned metadata/configuration header followed by normalized steps from one committed snapshot, without overwriting existing files.
- The CLI guide documents runnable authoring, inspection, recovery, and JSONL analysis contracts.
- A comprehensive test suite covers implemented behaviors with reusable fixtures under `tests/fixtures/`.
- Mailbox coverage includes disconnect/reconnect, parallel channels, shutdown/restart, process crashes, undelivered accepted answers, competing responses, idempotent retries, cancellation, and notification failures.
- LLM integration coverage includes state reconstruction, request mismatches, branching, cancellation, tool errors, compaction interruption, and linear saga-input storage growth. Provider tests use fakes rather than live model calls.
- Structured diagnostic logging persists versioned JSONL outside saga history, with UTC timestamps, severity filtering, task-local execution/workflow/step correlation, nested sensitive-field redaction, and metadata-only error frames.
- Bounded background writes, size rotation, count retention, private file permissions, and dropped/write-error counters keep diagnostics independent of workflow outcomes. Authenticated hosts can list retained files and download bounded byte chunks over either control transport; configuration and delivery guarantees are documented in [Structured diagnostic logs](docs/config/logging.md).
- Logging coverage includes redaction, queue overflow, disk failures, shutdown draining, rotation/restart, bounded downloads, parallel activity correlation, and replay.
- Workflow code reads schema-free nested component settings with `await configuration.get(name, default)`. Each read is a recorded `configuration.get` activity: completed reads replay their old values while new reads load the current workspace file off the event loop. There is no global configuration digest or component-schema registration.
- LLM generation and tool rounds read recorded configuration snapshots for omitted model/provider, thinking (`reasoning.effort`), temperature, output budget, timeouts, and compaction. Async `resolve_settings` supports workflow helpers; explicit parameters override workspace defaults. Existing LLM objects adopt live model changes on the next fresh round, while interrupted generations retry with their recorded settings.
- [Component configuration](docs/config/components.md) documents lookup semantics, persisted-value security, LLM precedence, round-limit scope, and history compatibility. Configuration values can safely drive workflow branches because reads participate in deterministic replay.
- Transient provider failures retry within the existing generation/compaction activity with configurable bounded exponential backoff, stable activity identity, partial-stream reset, cancellation propagation, and structured retry/error logs. Completed activities replay without retries; unfinished recovery starts a fresh bounded budget using recorded settings. [LLM retry and tool-error policies](docs/config/components.md#transient-provider-retries) document defaults and boundaries.
- Retry and tool-error coverage includes Connect error events, transient classification, bounded delays, partial/final attempt failures, replay, compaction, storage-failure isolation, cancellation, exact tool error text, strict handling, and correlated diagnostic logs.
- Runner-global configuration automatically creates and reuses separate encryption and control-authentication secrets in a private user-level directory. Daemon startup, local clients, and embedded mode no longer require per-start token provisioning; explicit token overrides remain supported.
- Provider credentials are stored in per-profile AES-GCM encrypted files with private permissions, atomic publication, and cross-process refresh serialization. The LLM adapter resolves credentials through the runner instead of environment variables; non-secret profile references participate in settings while default-profile request digests preserve history compatibility.
- ChatGPT OAuth is runner-owned: hosts claim pending authentication requirements, start their own loopback callback listener, open a browser, and relay state/code over authenticated control RPCs. The runner retains PKCE material, exchanges codes, persists tokens, and refreshes independently of host presence. Dedicated queries and advisory events support reconnects; authentication payloads never enter mailbox, saga, or control receipt storage.
- Missing API keys fail without prompting; interactive OAuth waits survive host disconnect and clean runner shutdown/recovery. Claims expire, stale callbacks are rejected, and explicit authentication cancellation fails shared waiters. Token endpoint failures are sanitized and classified, refresh retries are bounded, and rotated tokens finish publication before cancellation propagates.
- [Provider authentication](docs/config/authentication.md) documents provisioning, host coordination, RPC contracts, restart behavior, Unix filesystem requirements, and the trusted same-user execution boundary. Authentication coverage includes mocked token endpoints and host callback HTTP rather than live provider login.
- [Target environments](docs/development/target-environments.md) provide an async typed interface and a POSIX local filesystem backend, selected through optional workspace `[environment]` configuration with an absolute `base_project_path` separate from runner infrastructure. Operations include metadata, bounded listings and byte reads, incremental UTF-8 line reads, atomic single-file writes, mkdir, remove, and rename. Resolved-path validation is not race-resistant containment or a sandbox.
- Shared process-driver contracts, byte-cursor output buffers, and an environment-owned process manager support independent executions, stdin/EOF, polling, termination, session discovery, and shutdown. Running sessions survive individual call cancellation; completed sessions are released after output collection or retention expiry. Local execution is enabled with the local environment, and child environment variables follow parent inheritance, optional allow/deny filters, configured defaults, then command overrides.
- Each root workflow run attaches its configured environment and injects it into activity contexts. Child workflows borrow the same attachment; concurrent roots have independent process managers. Generic `ctx.resources.register(name, async_cleanup)` callbacks run once in reverse registration order after activities and children stop, with awaited cleanup on success, failure, cancellation, and suspension. Cleanup failures are reported without skipping remaining finalizers; repeated cancellation does not interrupt owned teardown. No saga or event-subscription dependency is introduced.
- `ExecRequest.kill_tree` defaults to true: local kill, timeout, and shutdown target the command's POSIX process group, and remaining group members are cleaned up when the command exits. Parent-only termination is available with `kill_tree=false`. Deliberately detached descendants and hard runner crashes remain outside the cleanup guarantee; recorded process IDs are not restored on resume.
- Operations using stale process IDs after environment recreation fail with `EnvironmentError` (`missing`) and instruct the caller to start a new process with `exec` and use its new ID. Poll, stdin writes, EOF, and kill do not silently respawn commands. The existing tool layer returns the error text directly to the LLM by default; retained terminal sessions still support final-output polling.
- Process-restart error coverage verifies environment recreation, replacement process execution, model-visible stale-ID errors, and replay without re-executing failed tool operations.
- Environment, process-management, and root-resource coverage includes bounded output, cancellation survival, environment-variable precedence, termination escalation, process-tree control, generic cleanup ordering/failures, child inheritance, concurrent-root isolation, and persistent-execution cleanup.
- One daemon now manages concurrent independent executions within a workspace while retaining exclusive project writer ownership. Start creates a new root; resume rejects duplicate active execution IDs; stop affects only the selected execution and waits for owned cleanup before terminal notification. Startup stops persist cancellation after history initialization. Roots retain separate histories, mailboxes, environment attachments, and process managers, but shared source-tree edits are not isolated.
- The execution-oriented control API adds paginated `executions.active` and typed client listing results. `executions.current` accepts an execution ID and rejects ambiguous no-ID queries; start, resume, stop, persisted lookup, history, and event subscriptions remain execution-specific. Daemon status/connect display active execution pages. [Control protocol](docs/reference/control-protocol.md#concurrent-execution-lifecycle) documents lifecycle and compatibility behavior.
- Cancel shutdown handles each root independently, preserving mailbox/authentication waits for restart without suspending unrelated work or overriding explicit stops. Drain waits for every root while accepting responses and reconnects. Active, scheduled, and reserved histories are protected against retention during startup, resume, and cleanup.
- Multi-execution coverage includes concurrent memory/TCP clients, independent failures and stops, idempotent start/resume, active pagination, event filtering, atomic state updates, legacy manifests, hard-crash recovery without a manifest, incomplete unpublished histories, multi-waiter restart, authentication isolation, drain/reconnect, cancelled/repeated shutdown, and retention protection.

## Verification

Keep this tracker focused on capabilities, coverage, and remaining work rather than test totals or per-feature pass counts. Use test and tool output for current validation results.

```bash
PYTHONASYNCIODEBUG=1 uv run pytest -W error
uv run black --check src tests
uv run mypy src
git diff --check
```

Format and type-check changed tests as well as production code. The broader `uv run mypy src tests` check has known typing issues in authentication and diagnostics tests; do not interpret production-only type checking as a clean full-test type check.

## Suggested next horizon

- Extend MCP interoperability where needed: resource templates/subscriptions, target-side server launch, additional OAuth registration/client modes and metadata layouts, and explicit scope escalation. Validate against real servers and define any new protocol capabilities before advertising them. Preserve selected-source checks, independent concrete-tool approval, bounded session ownership, and offline completed replay; interrupted remote side effects still have unknown outcomes. Do not introduce Knowlt integration.
- Extend target environments with Docker and SSH drivers using the shared process manager. Define connection ownership, target-side environment-variable policy, termination capabilities, and unknown outcomes; add PTY support independently. Persistent connections must still create a fresh managed process for each execution request.
- Add durable target identity/policy binding to prevent silent target changes on resume. Stale process IDs already return actionable errors without silently respawning commands; crash recovery and remote reattachment remain unimplemented and are not provided by runtime cleanup scopes.
- Evaluate compaction summary quality on long real conversations and model-specific usage semantics. Measured maintenance and bounded overflow recovery intentionally do not predict the next request's fit. Cross-model summary usage and hidden reasoning cannot supply exact replay costs; missing comparable measurements conservatively limit available cut points.
- Add configurable concurrency limits to the implemented parallel tool execution while preserving independently recorded calls, deterministic result ordering, and cancellation/replay behavior.
- Extend the implemented tool-policy registry with argument-aware matchers or host-managed execution-scoped grants as needed. Keep mandatory checks separate from auto-approval, define grant lifetime and revocation, and preserve outcome-only replay and durable per-call host confirmation.
- Extend structured diagnostics as needed with opt-in standard-library logging adapters, age-based retention, and richer provider metrics; preserve payload minimization and keep diagnostic events separate from saga history.
- Extend `run_agent` with workspace-configured catalogs or discovery if needed; preserve explicit permitted references, workflow-owned input validation, and durable spawn/join orchestration.
- Design a steering API for messages arriving when no input request is pending. Evaluate queued mailbox inputs and a nonblocking peek/receive API so the LLM loop can inject steering between rounds. Decide queue ownership, routing, persistence, consumption/acknowledgment, and deterministic replay semantics before changing the current request/response mailbox contract.
- Extend provider authentication beyond ChatGPT OAuth as needed, add encryption-key rotation tooling, and consider native platform-specific locking/storage support beyond the initial Unix implementation. Remote control continues to require a protected tunnel; direct remote TLS is not implemented.
- Add explicit CLI fork and execution-listing commands if needed.
- Add host-side mailbox presentation or HTTP adapters as needed without coupling them to workflow execution.
